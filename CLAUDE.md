# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Budget Tree" — a Flutter app (single-author CS project) that turns personal budgeting into a tree-growing metaphor: budgets are trees with expense "branches", and savings goals are "saplings" that grow as money is allocated to them over pay cycles. Heavy emphasis on hand-painted `CustomPainter` scenes (trunks, canopies, grass, leaves, weather) rather than off-the-shelf widgets.

## Commands

```bash
flutter pub get                 # install deps (run after changing pubspec.yaml)
flutter run                     # run on the default attached device/emulator
flutter run -d chrome           # run in the browser
flutter analyze                 # static analysis / lint (flutter_lints, see analysis_options.yaml)
flutter test                    # run all tests
flutter test test/widget_test.dart            # run a single test file
flutter test --plain-name "substring"         # run tests whose name matches
flutter build apk|ios|web|macos               # release builds
```

Pins Dart SDK `^3.11.5` (in `pubspec.yaml`); developed against Flutter 3.44+.

Run against Supabase with credentials from a gitignored `env.json`:

```bash
flutter run --dart-define-from-file=env.json   # injects SUPABASE_URL + SUPABASE_ANON_KEY
```

Database schema is managed with the Supabase CLI (migrations in `supabase/migrations/`, project linked to ref `uxfmisgzrprdzagfhcke`):

```bash
supabase migration new <name>   # scaffold a migration, then write SQL into it
supabase db push                # apply pending migrations to the linked remote DB
supabase migration list         # compare local vs remote
```

The AI coach runs in a Supabase **edge function** (`supabase/functions/ai-coach/`) that calls the Anthropic API. Deploy it and set the key as a secret (the key never ships in the app):

```bash
supabase functions deploy ai-coach
supabase secrets set ANTHROPIC_API_KEY=sk-ant-...
```

**Edge-function security (don't regress).** `verify_jwt` alone is not enough: the public anon key is a validly-signed JWT, so the function itself calls `supabase.auth.getUser()` and returns `401 unauthorized` for anyone who isn't a real signed-in user (the anon role is rejected). It then enforces a per-user hourly quota via the `check_ai_quota(max_calls)` SECURITY DEFINER function (backed by the RLS-locked `public.ai_usage` table, migration `20260705173327_ai_usage_ratelimit.sql`), returning `429 rate_limited` over `HOURLY_CALL_LIMIT` (30). Free-form inputs (`expenses`, `survey`, `synopsis`) are size-capped before hitting the prompt so a big payload can't amplify token cost. Errors return generic tokens (`internal_error`, `unauthorized`, `rate_limited`) — never internal detail. CORS ([_shared/cors.ts](supabase/functions/_shared/cors.ts)) echoes an origin only for localhost or the `ALLOWED_WEB_ORIGIN` secret, never `*`. Keep all of this when editing the function. Password policy is min 8 chars + a letter and a digit, enforced both server-side (`config.toml` `minimum_password_length=8` / `password_requirements="letters_digits"`, mirror in the hosted dashboard) and client-side (`isStrongPassword` in [login_screen.dart](lib/screens/auth/login_screen.dart), tested in [test/password_policy_test.dart](test/password_policy_test.dart)). The web build ships a hardening CSP in [web/index.html](web/index.html) (see comment there; a fully strict CSP needs `flutter build web --csp`).

## Workflow

After implementing any feature (major or minor), update this CLAUDE.md to reflect the change — new services/screens, added model fields, architectural shifts — then commit and `git push` to the current branch. Keep doc edits in the same commit as the feature when practical.

## Architecture

All real source lives under [lib/](lib/). (The top-level `services/` and `widgets/` directories are stray leftovers — the empty top-level `services/auth_service.dart` is **not** the real one, which is `lib/services/auth_service.dart` — ignore the top-level dirs; do not add code there. The empty `lib/blocs/` and `lib/components/` dirs are likewise unused — reusable pieces live in `lib/widgets/`, not there.) Long scroll views (the create-budget wizard steps, create-goal, settings, goals, friends, profiles) are wrapped in [AppScrollbar](lib/widgets/app_scrollbar.dart) — a small wrapper that owns a `ScrollController` and shows an always-visible thumb (`thumbVisibility`) so users can tell there's more content below the fold; pass the builder's controller to the single scroll view it wraps. The thumb colour comes from `scrollbarTheme` in `AppTheme.theme`.

**Entry & navigation.** [lib/main.dart](lib/main.dart) loads `AppSettings` before `runApp`, then wraps `MaterialApp` in an `AnimatedBuilder` on `AppSettings.instance` so theme/text-scale changes rebuild the whole app. Flow: [HomeScreen](lib/screens/home_screen.dart) (redesigned launch: neutral canvas, an `IllustrationCard` hero where a flat tree grows in with Acorn beside it, Fredoka title + pill Start) → 350ms fade → [DashboardScreen](lib/screens/dashboard_screen.dart) (the "four-leaf menu") which routes to the four pillars: Create Budget, Forest (view budgets), Goals, Settings. The [GuidedTour](lib/tutorial/tutorial_tour.dart) runs **from the dashboard** on first launch (HomeScreen captures `!tutorialSeen` when Start is pressed and passes `DashboardScreen(runTour: true)`; the dashboard plays the tour in a post-frame callback then sets `tutorialSeen`), so Acorn greets the user at the four-leaf menu *before* the Create flow and every tour section pops back to that menu. The social layer is **not** a pillar/screen — it lives directly on the dashboard: a **top-right profile button** (the user's [ProfileAvatar](lib/widgets/profile_avatar.dart) in an accent ring with a "Profile" label, `_ProfileButton`) pushes the user's own [ProfileScreen](lib/screens/profile_screen.dart), and a Roblox-style **[FriendsStrip](lib/widgets/friends_strip.dart)** (horizontal swipeable row of avatar circles between the banners and the menu grid) is the friends surface: its first circle is always "Add friends" (opens [FriendsScreen](lib/screens/friends_screen.dart)) with a tally badge (total friends, or "active/total" in green when any friend is active now), and each friend circle (avatar ringed green when active) opens their [FriendGardenScreen](lib/screens/friend_garden_screen.dart); under each circle the name row shows a green presence dot to the LEFT and the friend's goal-status emoji to the RIGHT. **Presence** is a `profiles.last_seen_at` column (migration `20260718015404_profile_presence.sql`): `ProfileService.touchPresence()` stamps it (throttled to once per 2 min, best-effort) on dashboard init and each return to the menu; `Profile.isActive` = seen within 5 min. The old swipe-in `endDrawer` (`SocialDrawer`/`SocialTabBar` and the edge handle) is **deleted** — ProfileScreen/FriendsScreen are plain pushed screens now (their optional `onClose` still swaps back for X). Navigation is plain imperative `Navigator.push` with `MaterialPageRoute`; there is no router package and no DI/state-management package. `main.dart` also calls `NotificationService.init()` before `runApp` and fires `NotificationScheduler.rescheduleAll()` unawaited on boot so first paint isn't blocked. It also calls `SupabaseConfig.init()`, `AuthService.instance.start()`, and `SyncEngine.init()` before `runApp`, and the app's `home` is an [AuthGate](lib/widgets/auth_gate.dart) that shows the email/password [LoginScreen](lib/screens/auth/login_screen.dart) until signed in, then routes through `OnboardingGate` (in auth_gate.dart) before the HomeScreen flow above. **Guest mode ("try it first")**: the login screen's tertiary "explore first" button (shown only when it's the gate root) calls `AuthService.enterGuestMode()` — a persisted flag (`guest_mode_v1`, restored in `start()`, which `main` awaits) that makes the AuthGate route the signed-out user to HomeScreen in local-only mode, so value comes before account creation. The launch screen's existing Sign In / Register controls are the upgrade path; any sign-in clears the flag and `SyncEngine.onSignedIn` pushes the guest's local rows up, so nothing is lost. The social tabs' "needs an account" notice carries a Create account button for guests, and `LoginScreen._openVerify` pops the pushed login screen after a successful verification so a guest upgrading mid-session doesn't land back on a stale form. When a guest plants their **first tree**, the dashboard swaps the "new tree" snackbar for a **one-time** account-upgrade bottom sheet (`AuthService.shouldOfferAccountUpgrade` / `markAccountUpgradeOffered`, key `guest_account_prompt_shown_v1`) — after that, the launch screen's Register button is the only nudge. Sign-up is just email+password, but it is **email-verified**: when Supabase "Confirm email" is on, `signUp` creates no session, so `LoginScreen` pushes [VerifyEmailScreen](lib/screens/auth/verify_email_screen.dart) where the user enters the 6-digit code emailed to them (`AuthService.verifyEmailOtp` → `verifyOTP(OtpType.signup)`, with `resendSignupOtp`); verifying creates the session and the gate advances (a sign-in attempt that throws `email_not_confirmed` is routed there too). **Requires dashboard config**: enable Confirm email and put `{{ .Token }}` in the "Confirm signup" email template so a code (not just a link) is sent. After verification **every account must claim a username**, so the gate sends any signed-in user without a profile through the forced [OnboardingScreen](lib/screens/onboarding_screen.dart) (username + optional display name) before the app opens — where **Acorn** (the `AcornMascot`) greets them in a speech bubble whose line reacts to the form state (welcome / busy / error). It's offline-first: once a user onboards, `ProfileService.markOnboardedLocally()` records their id locally (`onboarded_user_id_v1`) so later launches skip the network profile lookup; a profile-fetch failure shows a retry rather than locking the user out.

**Persistence — offline-first cache synced to Supabase.** Source of truth is **Supabase** (Postgres + email/password auth); `shared_preferences` is a local **write-through cache** so reads stay instant. The seam is [SyncedStore<T>](lib/services/synced_store.dart): reads return cache immediately then refresh in the background; writes hit cache first, then upsert/delete to Supabase (queued in a per-collection pending list when offline). The four stores keep their original static API (`loadAll`/`saveNew`/`update`/`delete`) and local cache keys, each delegating to a `SyncedStore`:
- [BudgetRepository](lib/services/budget_repository.dart) — cache `budget_tree_v1`, table `budgets`
- [GoalRepository](lib/services/goal_repository.dart) — cache `goals_v1`, table `goals`
- [CategoryRepository](lib/services/category_repository.dart) — cache `tree_categories_v1`, table `categories`
- [AchievementService](lib/services/achievement_service.dart) — cache `ach_unlocks_v1`, table `achievements`

Each Supabase table is keyed `(user_id, id)` with the whole model in a `data jsonb` column under per-user RLS, so **the toJson/fromJson rule still governs: when you add a model field, update both and keep the fallback** — it maps straight into `data`, no schema change needed. [AuthService](lib/services/auth_service.dart) (`AuthService.instance`, mirrors AppSettings) wraps Supabase auth; [SyncEngine](lib/services/sync_engine.dart) handles first-login migration (push local rows up, then pull), flush-on-resume/reconnect, and clear-caches-on-signout. No dart-defines → everything degrades to local-only mode. Schema lives in [supabase/migrations/](supabase/migrations/).

**Social layer — profiles, friends & shared goals (online-only).** Distinct from the four offline-first stores: the social services talk to Supabase **directly** and no-op when unconfigured/signed-out (they gate on `SupabaseConfig.isConfigured && AuthService.instance.isSignedIn`, surfacing an "online required" UI). While loading, both screens show layout-shaped skeleton placeholders ([lib/widgets/skeleton.dart](lib/widgets/skeleton.dart): `SkeletonPulse`/`SkeletonBox` + `FriendsSkeleton`/`ProfileSkeleton`, pulse gated on reduced motion) instead of bare spinners. Two extra tables (real columns, *not* the `data jsonb` pattern): `profiles` (one per user — unique `username`, optional `display_name`, free-text `bio`, plus `status_mode`/`status_goal_id` controlling how the user's status emoji is derived, and `last_seen_at` for presence) and `friendships` (`(requester, addressee, status)`). Privacy is **per-goal**: `Goal.sharedWithFriends` (default false, the single privacy toggle on [GoalDetailScreen](lib/screens/goal_detail_screen.dart)) gates an *additive* `"friends read shared goals"` SELECT policy on the `goals` table — an accepted friend can read only goals the owner marked shared. **Budgets are never shared.** A **profile** is just `username` + `bio` + the goals the user shared, drawn as saplings in a grid (the [GoalSaplingCard](lib/widgets/goal_sapling_card.dart), which renders each sapling in its goal's saved tree colour via `Goal.leafColorValue` and a `FittedBox` so the tree always fits the cell; completed goals read golden). The user sees their own via the dashboard's top-right profile button ([ProfileScreen](lib/screens/profile_screen.dart), bio editable there); a friend sees the same view via [FriendGardenScreen](lib/screens/friend_garden_screen.dart) (name + bio header + shared-goal grid). Tapping a sapling opens the goal: on your own profile that's the editable [GoalDetailScreen](lib/screens/goal_detail_screen.dart); on a friend's it's the **read-only** [FriendGoalScreen](lib/screens/friend_goal_screen.dart) (sapling in the owner's colour + progress, no deposit/edit/delete/share controls — friends can never alter your goals, which RLS also enforces; laid out as a Column mirroring GoalDetailScreen so the whole tree is always visible, guarded by [test/friend_goal_layout_test.dart](test/friend_goal_layout_test.dart)). Because categories are **never** synced between users, a goal carries a denormalised `leafColorValue` (its category's `colorValue`) in its `data` jsonb so a friend renders the same colour the owner saved; it's set when a goal is created/edited and backfilled-then-persisted when the owner opens their own ProfileScreen. (There is **no "featured goal"** mechanic — it was removed; the only goal-sharing control is the per-goal privacy toggle.) Profiles also carry an optional **profile picture** picked from the device gallery (`image_picker`, resized to ~256px JPEG on device and stored inline as base64 in `profiles.avatar_b64`, migration `20260706120000_profile_avatar.sql`; rendered by [ProfileAvatar](lib/widgets/profile_avatar.dart) on the own-profile header, friend tiles, and the friend garden app bar; iOS photo permission is declared in Info.plist). Services: [ProfileService](lib/services/profile_service.dart) (claim username, search, set status mode, set bio, set avatar, `touchPresence`), [FriendsService](lib/services/friends_service.dart) (requests, accept/remove, a friend's shared goals + assembled `FriendSummary`), and the pure [FriendStatus](lib/services/friend_status.dart) util (goals → one status emoji via the friend's `FriendStatusMode`). Username is claimed during onboarding (the forced [OnboardingScreen](lib/screens/onboarding_screen.dart) behind `OnboardingGate`) — required for **every** account, not just those who want friends. `ProfileService.claimUsername` accepts an optional `displayName` and marks the user onboarded locally on success; `FriendsScreen` still carries a `_ClaimUsername` fallback for the unconfigured-then-configured edge.

**App-wide settings.** [AppSettings](lib/services/app_settings.dart) is a `ChangeNotifier` singleton (`AppSettings.instance`) persisting palette, text scale, reduced-motion, the tutorial-seen flag, a `soundEnabled` toggle, an `aiCoachEnabled` toggle (master switch for the AI coach), and notification preferences (per-type toggles for budget warnings / streak reminders / weekly summary / goal watering reminders, plus the scheduled hour/minute/weekday for each, including `notifGoalWatering` + `waterHour`). Each setting has its own `settings_*_v1` key. UI reads `palette`/`textScaleFactor`/`motionMultiplier` from it; the whole app is theme-reactive through the listener in `main.dart`. Changing a notification setting should re-run `NotificationScheduler.rescheduleAll()`. It also holds the app `locale` (`settings_locale_v1`, null = follow device) used by a Language picker in Settings — see Localization below.

**Localization (i18n).** Flutter `gen-l10n`: strings live in ARB files under [lib/l10n/](lib/l10n/) (`app_en.arb` is the template, plus `app_fr.arb`, `app_es.arb`); `flutter gen-l10n` (or any build) regenerates `AppLocalizations` (also in `lib/l10n/`, committed). `main.dart` wires `localizationsDelegates`/`supportedLocales` and `locale: AppSettings.instance.locale`, so the Settings language picker (English / Français / Español / System) flips the whole app live. In widgets read strings via `AppLocalizations.of(context).<key>` (non-null getter). **To add a string: add the key to all three ARB files, run `flutter gen-l10n`, then reference it.** The **whole app is localized** — every screen, dialog, the Acorn tutorial dialogue, achievements, allocation suggestions, and notifications. Patterns to reuse: data/model labels live in `lib/l10n/` extension helpers (`goal_labels.dart`, `achievement_labels.dart`, `preset_labels.dart`); background code with no `BuildContext` (notifications) resolves strings via `appLocalizations()` in `app_localizations_resolver.dart`; pure services/data functions that produce copy take an `AppLocalizations` param (e.g. `SuggestionService.forBudget`, the `tutorial_content.dart` functions). **Never hardcode user-facing copy, and never use dashes in it** (em-dashes/hyphens read as AI — reword; ranges become "3 to 20", clauses become separate sentences). Mandatory French grammar hyphens (e.g. `Connectez-vous`) are the only exception.

**Theming is token-driven.** The app has the modern minimal look: warm beige canvas (`#F1EBDE`), soft cream cards with gentle shadows, color delivered through flat illustrations and a fresh green accent. Source of truth is [lib/theme/app_tokens.dart](lib/theme/app_tokens.dart): `Conifer` (the 11-stop green accent ramp, `c50`–`c950`) and `AppTokens` (semantic roles — `canvas`, `canvasSoft`, `card`, `cardBorder`, `textPrimary/Secondary/Tertiary`, `accent`, `accentStrong`, `accentSoft`, `accentTint`, `onAccent`, `success/warning/danger`, `skyTint`, `soilTint`) with const `light`/`dark` instances. Read via `AppTokens.current` (works inside CustomPainters, no context needed) or `AppTokens.of(context)`; the whole app rebuilds through the `AnimatedBuilder` on `AppSettings.instance` in main.dart, so token reads stay live when the theme flips. `AppPalette` is now `{light, dark}` (light default, persisted at `settings_theme_mode_v1`; the legacy 3-dark-palette key is ignored). [app_theme.dart](lib/theme/app_theme.dart) builds `AppTheme.light`/`AppTheme.dark` from the tokens (Fredoka display + Nunito body set once in `textTheme`, pill buttons, themed inputs/sheets/dialogs/snackbars/chips/switches); main.dart picks by `AppSettings.instance.isDark`. Shape/spacing constants live in [app_dims.dart](lib/theme/app_dims.dart) (card radius 24, inner 16, sheet 28, pill; 4pt spacing scale). [app_shadows.dart](lib/theme/app_shadows.dart) recipes are brightness-aware (soft ambient in light, deeper in dark). `leaf_palette.dart` (4-stop leaf ramp from an accent via HSL, default now conifer) and `category_icons.dart` are unchanged in role. **Compat alias:** `AppColors` remains in app_theme.dart as theme-aware getters over the token roles (text/surface/accent members follow light/dark automatically; a few fixed hues like `barkBrown`/`riverBlue` stay const) so older call sites keep working — do not add new uses; write `AppTokens` in new code. `AppPalettes`, `BarkCard`, `VineStepIndicator`, and the stray `viewbudgets_screen` are deleted. **Dark mode ships**: Settings → Appearance → Theme (Light/Dark segmented picker), persisted at `settings_theme_mode_v1`. New surfaces use the **component kit in [lib/widgets/ui/](lib/widgets/ui/)**: `AppCard` (white card; constructor mirrors the retired BarkCard), `IllustrationCard` (tinted illustration container), `AppPrimaryButton`/`AppSecondaryButton`/`AppTextButton`, `PressableScale` (spring press feedback on every tappable), `Entrance`/`StaggeredColumn` (fade+slide entrances), `AppProgressBar`, `SegmentedChoice<T>`, `SectionHeader`. Every micro-animation must scale by `AppSettings.instance.motionMultiplier` or gate on `motionFull` so reduced motion actually stops it.

### Domain model

- **Budget** ([budget_model.dart](lib/models/budget_model.dart)): `BudgetModel` (tree) → `IncomeSource`s + `ExpenseCategory`s (branches). An `IncomeSource` carries its own arrival rhythm (`frequency`, a nullable `PayFrequency`; null = legacy "once per cycle") and `amountPerCycle(cycle)` converts it into the budget's cycle via `periodsPerMonth` ratios — so a $2000 bi-weekly salary counts as ~$4333 in a monthly budget. An `ExpenseCategory` carries the **same rhythm mechanic for bills**: `frequency` (nullable, null = once per cycle) with `allocatedPerCycle(cycle)` / `setAllocatedPerCycle(perCycle, cycle)`, so $1200 monthly rent in a weekly budget reads as a ~$277 per-cycle **set-aside** (surfaced as advice in the wizard's branch list, the branch detail sheet's `setAsideEachCycle` line, and the forest edit sheet, which also lets each branch's rhythm be edited). `BudgetModel.payFrequency` doubles as **the budget's cycle**: `totalIncome` sums `amountPerCycle(payFrequency)` and `totalAllocated`/`percentageFor`/`remaining` sum `allocatedPerCycle(payFrequency)`, keeping both sides like-for-like (tested in [test/income_cycle_test.dart](test/income_cycle_test.dart)). `PayScheduler` credits linked goals with the branch's **per-cycle** allocation for each elapsed period; AI `budget_plans` payloads convert expense amounts to per-cycle before sending, and applied plan amounts convert back into the bill's own rhythm. An `ExpenseCategory` holds `linkedGoalIds` connecting a branch to goals. Derived getters: `totalIncome`, `totalAllocated`, `remaining`, `percentageFor`. `PayFrequency` display names are localized via [lib/l10n/pay_frequency_labels.dart](lib/l10n/pay_frequency_labels.dart) (the enum itself is copy-free and has a `wire` token for the edge function).
- **Goal** ([goal_model.dart](lib/models/goal_model.dart)): a sapling. `targetAmount <= 0` means **uncapped** (`isUncapped`) — it grows forever through size `tier`s (1–6) on a log curve; capped goals use linear `progress` 0..1 and a `stage` 0–5. Visual growth/scale (`progress`, `stage`, `tier`, `tierScale`, `stageName`) all derive from these — don't store visual state. Every deposit/withdrawal is recorded in `contributions` (`List<Contribution>`, each dated and sourced: manual / auto / adjustment) — this ledger is the source of truth for streaks, comparisons, and achievements. The legacy `currentAmount` field still persists for back-compat; keep both in sync. **Completion is a durable trophy**: `isComplete` is the live "at/over target" check, but `completedAt` is stamped once (via `stampCompletionIfReached()`) and **never cleared** — `isCompleted` (`completedAt != null`) stays true even after a withdrawal and drives the golden card border + "Completed" filter on GoalsScreen and profile featuring. `sharedWithFriends` (default false) opts the goal into the social read policy (see the Social layer above). `leafColorValue` (nullable int) is a denormalised copy of the goal's category colour so a shared goal carries its tree tint to friends who can't see the owner's categories (null falls back to forest green). A goal can also carry a **watering schedule** (`waterAmount`, `waterCadenceIndex` → a [WaterCadence](lib/data/water_cadence.dart) weekly/biweekly/monthly, `nextWaterDate`, `waterRemindersEnabled`) set in the goal wizard; it drives reminder notifications only (the user still deposits manually). `advanceWatering()` rolls `nextWaterDate` forward past missed slots; a manual deposit on [GoalDetailScreen](lib/screens/goal_detail_screen.dart) pushes it one cadence out and reschedules.
- **TreeCategory** ([category_model.dart](lib/models/category_model.dart)): user tag shared by budgets and goals; its `colorValue` drives leaf color. Created **and deleted** via [CategoryPicker](lib/widgets/category_picker.dart) (tap "New" to add; long-press a category chip to delete — budgets/goals that referenced it just lose their tint, no cascade). `CategoryRepository.delete(id)` removes it.
- **Achievement** ([achievement.dart](lib/models/achievement.dart)): badge definition + `AchievementStats` (aggregate facts unlock tests read) + `AchievementCatalog` (predefined badges the service evaluates).

**Editing a saved tree & leftover money.** The forest grid card's edit sheet edits the tree name, category, branch amounts + charge rhythms, AND the roots (income sources: name, amount, arrival rhythm, add/remove) — and preserves `payFrequency`/`firstPayDate`/`lastProcessedAt` so an edit never resets the pay engine. When a budget has leftover (`remaining > 0`), the expanded forest card offers "Grow a goal with it": [routeLeftoverToGoal](lib/services/leftover_to_goal.dart) lets the user pick or quick-create a goal and appends a linked funding branch (same mechanic as the wizard's leftover step). The Gardener's Tips sheet on the budget tree ([SuggestionService](lib/services/suggestion_service.dart)) is goal-aware: pass `goals:` and it suggests a watering branch for every active goal the budget doesn't feed, plus a savings branch when leftover is large (>25% of income or >$200).

### Pay-cycle engine

[PayScheduler](lib/services/pay_scheduler.dart) is the core financial logic. `runUpdate(budget)` figures out how many whole pay periods elapsed since `budget.lastProcessedAt` (using `payFrequency` from [pay_frequency.dart](lib/data/pay_frequency.dart)) and credits each branch's allocation share to its linked goals, respecting target caps, then advances `lastProcessedAt` by exactly the processed periods (not to "now") and persists touched goals/budget. It's a pure-ish static utility — keep new financial math here, not in widgets. (There is **no tax feature** — tax estimation was removed; `BudgetModel.age`/`location` linger only for back-compat and are no longer collected.)

### Retention & engagement

A cluster of static-utility services drives streaks, badges, and reminders off the goal contribution ledger — keep this logic here, not in widgets:
- **StreakService** — weekly contribution streaks from the ledger.
- **PulseService** — pure picker for the dashboard's [PulseStrip](lib/widgets/pulse_strip.dart) (rendered above the ReflectionBanner; both banners are deliberately slim — one-line body, small icon — so the friends strip and menu grid keep room): returns the single most useful nudge in priority order — watering due/overdue (earliest `nextWaterDate`, deep-links to GoalDetailScreen) → streak at risk → quiet streak badge (both open GoalsScreen) → "plant your first tree" for empty accounts → hidden. The strip is the in-app face of the watering/streak habit (notifications are the out-of-app one); the dashboard refreshes it via a `GlobalKey<PulseStripState>` after every navigation. Unit-tested in [test/pulse_service_test.dart](test/pulse_service_test.dart).
- **ComparisonService** — week-over-week / month-over-month savings & allocation deltas.
- **SuggestionService** — allocation suggestions surfaced to the user.
- **AchievementService** — evaluates `AchievementCatalog` against `AchievementStats` and persists unlocks.
- **NotificationContent** — pure copy + severity logic. Note: a "budget warning" measures allocation-vs-income (there is no per-category spend log).
- **NotificationScheduler** — decides *what* to schedule (budget warnings, daily streak reminder, weekly summary, and **per-goal watering reminders**); **NotificationService** is the thin OS wrapper over `flutter_local_notifications` (channels: budget_warnings, streak_reminders, weekly_summary, goal_watering) that degrades failures to no-ops. Watering reminders are one-shot `zonedSchedule` notifications: for each goal with a schedule, `rescheduleAll()` seeds a "due in 2 days" heads-up and a "due today" nudge (at `AppSettings.waterHour`) and re-seeds the next occurrence on every boot/resume/deposit. **OS permission is requested on opt-in, not at boot**: `rescheduleAll()` only calls `NotificationService.requestPermissions()` once `AppSettings.notifPermissionAsked` is set, which happens when the user touches the Settings notifications card or saves a goal with "Remind me to water" on — a fresh install never opens with a permission dialog.
- **SoundService** — tactile/audible feedback, gated on `AppSettings.soundEnabled`.

### AI coaching (smart plans + reflections)

Claude (Sonnet) is woven into the core flows through a Supabase **edge function** ([supabase/functions/ai-coach/index.ts](supabase/functions/ai-coach/index.ts)) — the architecture is App → Edge Function → Anthropic API, so the `ANTHROPIC_API_KEY` stays server-side (set as a Supabase secret, never in the app). The function is one router switched on an `action` field with three actions, each returning strict JSON the app parses defensively: `budget_plans` (income + expenses each with an optional fixed amount + a **lifestyle questionnaire** (`survey`, question→answer) + an optional free-text note + the budget's `cycle` (`PayFrequency.wire`) so the coach scales estimates to the period, since amounts are per cycle rather than always monthly → 2-3 allocation plans that keep any fixed amounts and estimate the blanks from the survey), `goal_plans` (goal + target date + free monthly income → **watering plans** each as a `{cadence: weekly|biweekly|monthly, perWatering, monthsToTarget}` + alternative dates), and `reflection` (a compact period summary → 2-4 sentences of prose). The app sends **already-computed summaries**, never raw rows, so the function is stateless and cheap. The AI writes its prose in the app's active locale (passed as `locale`). Model is pinned to `claude-sonnet-4-6`.

Client side, everything is **online-only and degrades gracefully** (same gating as the social layer):
- [AiCoachService](lib/services/ai_coach_service.dart) (`AiCoachService.instance`) wraps `functions.invoke('ai-coach', ...)`, gated on `SupabaseConfig.isConfigured && AuthService.instance.isSignedIn && AppSettings.aiCoachEnabled`; it throws a typed `AiUnavailable` on any failure so callers fall back. DTOs in [lib/models/ai_plan.dart](lib/models/ai_plan.dart) (`AllocationPlan`; `GoalPlanOption` carries a `WaterCadence` + `perWatering` with a derived `monthly`; `GoalPlanResult`).
- **Budget creation** ([createbudget_screen.dart](lib/screens/createbudget_screen.dart)) is a **4-step wizard**: Income → Expenses → **Survey** → **Plan** (there is no separate Name & pay step — once allocations settle, the Plan step reveals the finishing touches below: tree name + pay schedule cards, and the bottom bar becomes "Plant My Budget Tree", gated on `_planSettled`). Each income gets its own arrival-rhythm chips ("How often does it arrive?") and the running list shows the per-cycle conversion (`approxEachCycle`) when the rhythms differ. The Plan step's pay card repeats the same cycle chips (still adjustable) plus the first-pay-date picker. Changing cycle/income resets `_planSettled`. **Every phase uses progressive disclosure** (the survey's one-at-a-time feel, generalised): a step opens with just its first box and reveals the next only after the user confirms the current one, via the shared `_Reveal` (fade + slide-in on first build) and `_ContinueButton` widgets. Income: the **add-a-source** box shows first; adding sources reveals the list, then a "That's all my income" button reveals the **budget cycle** card (`_payFrequency`, default monthly, so every later amount reads "per cycle"). Expenses: **add-a-branch** first, with a "That's all my expenses" confirm button unlocking Next. The **"where you stand" meter is pinned** above the scrolling content of both the Expenses and Plan steps (`_AllocationStrip`: allocation bar + allocated/remaining, amounts in `FittedBox`es so the full number always shows, red border when over) so what's left to allocate is never out of sight. Each expense also gets **charge-rhythm chips** ("How often is it charged?", `expenseCharged`) mirroring income's arrival chips, and the branch list shows the bill's rhythm plus its `approxEachCycle` set-aside when the rhythms differ. Reveal state lives in the parent (`_incomeConfirmed` / `_expensesConfirmed`, reset if the list is emptied) and **gates the bottom bar's Next**, so the disabled Next signals "finish this box". Next is additionally gated by a **scroll-through gate** (`_seenEnd`/`_noteScrollMetrics`, fed by `ScrollNotification` + `ScrollMetricsNotification` listeners around the step switcher): the user must have scrolled to the end of the current step before advancing, steps whose content fits pass automatically, and revealed content that grows past the fold re-arms the gate; when the gate is the only blocker the bottom bar shows a localized "scroll to the end" hint (`scrollToContinue`). Tests that drive the wizard must scroll to the end of a step before tapping Next (see the `scrollToEnd` helper in [test/create_budget_over_budget_test.dart](test/create_budget_over_budget_test.dart)). **Over-budget is a hard stop**: tapping Next on the Expenses or Plan step while `_totalAllocated > _totalIncome` doesn't advance — Acorn pops up (`showTutorialDialog`, `tutOverBudget1/2`) telling the user how far over they are and to trim before continuing (tested in [test/create_budget_over_budget_test.dart](test/create_budget_over_budget_test.dart)). The Plan step's finishing-touch cards are wrapped in `_Reveal` too. Income/Expense steps are intentionally decluttered (one hero input + a running list; quick-picks/presets demoted to a quiet `Wrap`). Expense amounts stay **optional**. The **Survey** step (`_SurveyStep`, questions defined in [lib/l10n/survey_labels.dart](lib/l10n/survey_labels.dart)) shows the lifestyle questionnaire **one question at a time**: tapping an answer auto-advances (short delay so the selection lands visually), each question has a Skip, a thin progress bar tracks position, and previously settled questions render as compact tappable recap rows so any earlier answer can be edited; once every question is answered/skipped it settles on a summary view with the optional free-text note. Answered/skipped state lives in the parent (`_surveyAnswers` / `_surveySkipped`) so leaving and re-entering the step resumes at the summary. Answers are sent to `budget_plans` as `survey` so the coach can estimate the blank expenses. The **Plan** step renders the coach's [AllocationPlanCard](lib/widgets/allocation_plan_card.dart)s (pick one or set amounts manually), and once settled offers **"Grow a goal with your leftover"**: route the remaining money to a new or existing goal, which appends an `ExpenseCategory` branch linked to that goal (`linkedGoalIds`) so `PayScheduler` auto-funds it.
- **Goal creation** ([create_goal_screen.dart](lib/screens/create_goal_screen.dart)) is a **3-step wizard** (Goal + amount → Timeframe → Watering plan); both wizards use the shared [StepProgress](lib/widgets/ui/step_progress.dart) segmented bar (the old vine indicator is deleted). The Watering step **asks whether to use the coach** (`_AiPrompt`); AI plans come back as selectable **watering** cards ("$X every 2 weeks", `_WaterPlanCard`), there is always a **Custom** card (cadence chips + per-watering amount), tappable alternative dates, and a **"Remind me to water"** toggle. Manual/offline uses [GoalPlanMath](lib/services/goal_plan_math.dart) (`monthlyToReach`/`perWateringToReach`/`monthsForPerWatering`). After saving it still offers to **link a budget branch** for auto-funding. `freeMonthlyIncome` (sum of budgets' remaining) is fed into the AI call.
- **Reflections** ([ReflectionService](lib/services/reflection_service.dart)): on boot/resume, `maybeGenerate()` checks whether a new weekly/monthly reflection is due (prefs-based dedupe), builds the summary from `ComparisonService`/`StreakService`/budgets/linked goals, calls the `reflection` action, caches the latest in `SharedPreferences` (so it shows offline) AND upserts to the `ai_reflections` table (per-user RLS, [migration](supabase/migrations/20260628140000_ai_reflections.sql)), then fires a local notification. The dashboard shows the latest via [ReflectionBanner](lib/widgets/reflection_card.dart); `NotificationScheduler` uses the cached reflection text as the scheduled weekly-summary body when present. Toggle: `AppSettings.aiCoachEnabled` (Settings → AI Coach).

### Painted scenes & tutorial

Screens sit on the flat token canvas; illustration lives in dedicated widgets, drawn flat (bold shapes, flat fills with flat light/dark caps, no gradients/blur shadows). The canonical pieces: [tree_drawing.dart](lib/widgets/tree_drawing.dart) (`TreeDrawing.paintTrunk/paintBranch/paintCluster/paintLeafFringe` — the budget tree, used by the animated `_GrowingTreePainter`, `StaticBudgetTreeView`, and forest `_MiniTreePainter`), [sapling_view.dart](lib/widgets/sapling_view.dart) (goal sapling stages), [acorn_mascot.dart](lib/widgets/acorn_mascot.dart) (flat two-tone Acorn, blink/sway/talk; the nut/face is a single flat tan with no shading crescent), home's `_HeroTreePainter`, and the dashboard's `_TileArtPainter` spot illustrations. **App launcher icon**: [app_logo.dart](lib/widgets/app_logo.dart) (`AppLogo` / `AppLogoPainter`) is the brand mark — the hero tree scene on the `Conifer.c50` tint, full-bleed, **without Acorn**. It's the source of truth for the launcher icon: `flutter test tool/gen_app_icon.dart` renders it to `assets/icon/app_icon.png` (1024²), then `dart run flutter_launcher_icons` (config + dev dep in pubspec.yaml) stamps every platform (Android legacy + adaptive, iOS, macOS, web). Re-run both after changing the logo art. [scenery.dart](lib/widgets/scenery.dart) keeps only `paintTreeSilhouette`, `paintLeaf`, and `paintFlower` (used by the budget-tree scene and immersive forest); the canopy/vine/firefly/light-shaft helpers are deleted. Outdoor scenes (budget tree, immersive forest) use a light `skyTint → canvas` wash + flat sun + conifer-tinted treeline + flat ground bands. Performance idioms: wrap animated painters in `RepaintBoundary` and implement `shouldRepaint` precisely. The hands-on onboarding lives in [lib/tutorial/](lib/tutorial/) — `GuidedTour` narrates *and* hands the user real screens; the speech bubble is a white card (the scrim stays dark in both themes). The in-screen `AcornCoach` (the draggable "Acorn's tip" panel, now a white card) can be swiped off the left/right edge to tuck away (leaving an edge handle to tap/swipe back), and re-opens itself when its `lessonKey` changes. **Every Acorn dialogue surface shares the same localized advance affordance**: the `TapContinueHint` widget (hint text + blinking chevron, exported from [tutorial_overlay.dart](lib/tutorial/tutorial_overlay.dart)) is used by both the full-screen overlay and the coach panel (`coachGotIt` on a tip's last line), and every coach string (`coachAcornTip`, tooltips via `howThisWorks`) comes from the ARB files — no hardcoded copy. Acorn's intro *and* closing tour dialogue point out the per-screen `SectionInfoButton` (`tutIntroHelp`) as the way to ask for help again. **Coach highlighting**: a `TutorialStep` can carry a `highlightId` (ids in `CoachTargets`); `CreateBudgetScreen` registers a `GlobalKey` per id (income/expense add boxes, allocation meter, survey area, plan area, finishing cards, the Next button) and passes the map as `AcornCoach.targets`, and while such a line is on screen the coach draws a pulsing `TargetHighlightRing` around the widget it's talking about (skipped silently if the target isn't laid out; anchor keys sit *outside* `AnimatedSwitcher`s so they never exist twice mid-transition).

**Planting a tree — the "planted" signal.** Completion is reported up the navigation chain, not inferred by re-counting (counting raced with the background Supabase pull and used to make the tutorial's Create step restart). On a brand-new tree's first save, `BudgetTreeScreen` pops with `true`; `CreateBudgetScreen._plantTree` forwards that `true` up; the dashboard's `_openCreate` then lands back on the four-leaf menu and shows the "new tree in your forest" snackbar, and `GuidedTour` treats the `true` as authoritative completion (falling back to a repo count). Updates to an already-saved tree (opened from the forest) keep the old snackbar + `popUntil(isFirst)` path — the new-vs-update split is `budget.savedAt == null` captured before stamping.

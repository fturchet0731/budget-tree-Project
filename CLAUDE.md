# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Budget Tree" — a Flutter app (single-author CS project) that turns personal budgeting into a tree-growing metaphor: budgets are trees with expense "branches", and savings goals are "saplings" that grow as money is allocated to them over pay cycles. Heavy emphasis on hand-painted `CustomPainter` scenes (trunks, canopies, grass, leaves, weather) rather than off-the-shelf widgets.

## Commands

```bash
flutter pub get                 # install deps (run after changing pubspec.yaml)
flutter run                     # run on the default attached device/emulator
flutter run -d chrome           # run in the browser
flutter analyze                 # static analysis / lint (flutter_lints, see analysis_options.yaml)
flutter test                    # run all tests
flutter test test/widget_test.dart            # run a single test file
flutter test --plain-name "substring"         # run tests whose name matches
flutter build apk|ios|web|macos               # release builds
```

Pins Dart SDK `^3.11.5` (in `pubspec.yaml`); developed against Flutter 3.44+.

Run against Supabase with credentials from a gitignored `env.json`:

```bash
flutter run --dart-define-from-file=env.json   # injects SUPABASE_URL + SUPABASE_ANON_KEY
```

Database schema is managed with the Supabase CLI (migrations in `supabase/migrations/`, project linked to ref `uxfmisgzrprdzagfhcke`):

```bash
supabase migration new <name>   # scaffold a migration, then write SQL into it
supabase db push                # apply pending migrations to the linked remote DB
supabase migration list         # compare local vs remote
```

The AI coach runs in a Supabase **edge function** (`supabase/functions/ai-coach/`) that calls the Anthropic API. Deploy it and set the key as a secret (the key never ships in the app):

```bash
supabase functions deploy ai-coach
supabase secrets set ANTHROPIC_API_KEY=sk-ant-...
```

**Edge-function security (don't regress).** `verify_jwt` alone is not enough: the public anon key is a validly-signed JWT, so the function itself calls `supabase.auth.getUser()` and returns `401 unauthorized` for anyone who isn't a real signed-in user (the anon role is rejected). It then enforces a per-user hourly quota via the `check_ai_quota(uid, max_calls)` SECURITY DEFINER function (backed by the `private.ai_usage` table, which lives **outside the API-exposed schemas** (`config.toml` exposes only `public` and `graphql_public`) so it has no REST endpoint at all rather than one that answers with an empty array; RLS stays on it as a second barrier, migrations `20260705173327_ai_usage_ratelimit.sql` and `20260802221910_harden_security_advisories.sql`), returning `429 rate_limited` over `HOURLY_CALL_LIMIT` (30). **It is called with the service role and an explicit user id**, not by the signed-in user against `auth.uid()`: that lets it be granted to `service_role` alone, so it is not reachable at `/rest/v1/rpc/check_ai_quota` where a user could spend their own quota. The id can't be spoofed because it comes from the already-validated `getUser()` call, never from the request body. If you ever `create or replace` it, **re-run the revoke** — Postgres grants EXECUTE to PUBLIC on a newly created function. **Every action rebuilds its prompt payload from an allow-list** rather than forwarding the request body: `budget_plans` caps `expenses`/`survey`/`synopsis`/`currency`/`locale`, `goal_plans` caps the goal name and coerces its numbers plus validates `targetDate` against `^\d{4}-\d{2}-\d{2}$`, and `reflection` reconstructs `{period, budgets, week, month, streakWeeks, linkedGoals}` with bounded lists (`MAX_BUDGETS`, `MAX_LINKED_GOALS`) and truncated names instead of sending the raw body. The shared `num()`/`str()`/`arr()` helpers do the coercion, so a big or malformed payload can't amplify token cost or crash prompt assembly. Errors return generic tokens (`internal_error`, `unauthorized`, `rate_limited`) — never internal detail. CORS ([_shared/cors.ts](supabase/functions/_shared/cors.ts)) echoes an origin only for localhost or the `ALLOWED_WEB_ORIGIN` secret, never `*`. Keep all of this when editing the function. Password policy is min 8 chars + a letter and a digit, enforced both server-side (`config.toml` `minimum_password_length=8` / `password_requirements="letters_digits"`, mirror in the hosted dashboard) and client-side (`isStrongPassword` in [login_screen.dart](lib/screens/auth/login_screen.dart), tested in [test/password_policy_test.dart](test/password_policy_test.dart)). The web build ships a hardening CSP in [web/index.html](web/index.html) (see comment there; a fully strict CSP needs `flutter build web --csp`). **Every script is same-origin or gstatic**: the passkeys SDK is vendored at `web/passkeys_bundle.js` rather than fetched from its GitHub release URL, which was mutable and therefore unpinned despite the version in the path. Do not delete that script tag even though the app never uses passkeys — `PasskeysWeb.registerWith` probes for `window.PasskeyAuthenticator` and calls `window.close()` when it is missing. Re-vendor it (and update the sha384 in the comment) when bumping `supabase_flutter`.

**`public.rls_auto_enable()` is a guardrail, not cruft.** It backs the `ensure_rls` `ddl_command_end` event trigger and automatically enables RLS on every new table created in `public`, so forgetting it in a migration cannot silently leave a table world-readable (verified: a probe table came out with `relrowsecurity = true`). It returns `event_trigger`, so it was never callable over RPC in the first place; its `anon`/`authenticated` EXECUTE grants were revoked in `20260802221910` purely to silence the advisor, which does not affect the trigger because event triggers don't check EXECUTE. **Don't drop it.**

## Workflow

After implementing any feature (major or minor), update this CLAUDE.md to reflect the change — new services/screens, added model fields, architectural shifts — then commit and `git push` to the current branch. Keep doc edits in the same commit as the feature when practical.

## Architecture

All real source lives under [lib/](lib/). (The top-level `services/` and `widgets/` directories are stray leftovers — the empty top-level `services/auth_service.dart` is **not** the real one, which is `lib/services/auth_service.dart` — ignore the top-level dirs; do not add code there. The empty `lib/blocs/` and `lib/components/` dirs are likewise unused — reusable pieces live in `lib/widgets/`, not there.) Long scroll views (the create-budget wizard steps, create-goal, settings, goals, friends, profiles) are wrapped in [AppScrollbar](lib/widgets/app_scrollbar.dart) — a small wrapper that owns a `ScrollController` and shows an always-visible thumb (`thumbVisibility`) so users can tell there's more content below the fold; pass the builder's controller to the single scroll view it wraps. The thumb colour comes from `scrollbarTheme` in `AppTheme.theme`.

**Entry & navigation.** [lib/main.dart](lib/main.dart) loads `AppSettings` before `runApp`, then wraps `MaterialApp` in an `AnimatedBuilder` on `AppSettings.instance` so theme/text-scale changes rebuild the whole app. Flow: [HomeScreen](lib/screens/home_screen.dart) (redesigned launch: neutral canvas, an `IllustrationCard` hero where a flat tree grows in with Acorn beside it, Fredoka title + pill Start) → 350ms fade → [DashboardScreen](lib/screens/dashboard_screen.dart) (the "four-leaf menu") which routes to the four pillars: Create Budget, Forest (view budgets), Goals, Settings. The [GuidedTour](lib/tutorial/tutorial_tour.dart) runs **from the dashboard** on first launch (HomeScreen captures `!tutorialSeen` when Start is pressed and passes `DashboardScreen(runTour: true)`; the dashboard plays the tour in a post-frame callback then sets `tutorialSeen`), so Acorn greets the user at the four-leaf menu *before* the Create flow and every tour section pops back to that menu. The social layer is **not** a pillar/screen — it lives directly on the dashboard: a **top-right profile button** (the user's [ProfileAvatar](lib/widgets/profile_avatar.dart) in an accent ring with a "Profile" label, `_ProfileButton`) pushes the user's own [ProfileScreen](lib/screens/profile_screen.dart), and a Roblox-style **[FriendsStrip](lib/widgets/friends_strip.dart)** (horizontal row of avatar circles docked directly above the menu grid; the circles are centered while they fit and become a swipeable row once they overflow) is the friends surface: its first circle is always "Add friends" (opens [FriendsScreen](lib/screens/friends_screen.dart)) with a tally badge (total friends, or "active/total" in green when any friend is active now), and each friend circle (avatar ringed green when active) opens their [FriendGardenScreen](lib/screens/friend_garden_screen.dart); under each circle the name row shows a green presence dot to the LEFT and the friend's goal-status emoji to the RIGHT. **Presence** is a `profiles.last_seen_at` column (migration `20260718015404_profile_presence.sql`): `ProfileService.touchPresence()` stamps it (throttled to once per 2 min, best-effort) on dashboard init and each return to the menu; `Profile.isActive` = seen within 5 min. The old swipe-in `endDrawer` (`SocialDrawer`/`SocialTabBar` and the edge handle) is **deleted** — ProfileScreen/FriendsScreen are plain pushed screens now (their optional `onClose` still swaps back for X). Navigation is plain imperative `Navigator.push` with `MaterialPageRoute`; there is no router package and no DI/state-management package. `main.dart` also calls `NotificationService.init()` before `runApp` and fires `NotificationScheduler.rescheduleAll()` unawaited on boot so first paint isn't blocked. It also calls `SupabaseConfig.init()`, `AuthService.instance.start()`, and `SyncEngine.init()` before `runApp`, and the app's `home` is an [AuthGate](lib/widgets/auth_gate.dart) that shows the email/password [LoginScreen](lib/screens/auth/login_screen.dart) until signed in, then routes through `OnboardingGate` (in auth_gate.dart) before the HomeScreen flow above. **Guest mode ("try it first")**: the login screen's tertiary "explore first" button (shown only when it's the gate root) calls `AuthService.enterGuestMode()` — a persisted flag (`guest_mode_v1`, restored in `start()`, which `main` awaits) that makes the AuthGate route the signed-out user to HomeScreen in local-only mode, so value comes before account creation. The launch screen's existing Sign In / Register controls are the upgrade path; any sign-in clears the flag and `SyncEngine.onSignedIn` pushes the guest's local rows up, so nothing is lost. The social tabs' "needs an account" notice carries a Create account button for guests, and `LoginScreen._openVerify` pops the pushed login screen after a successful verification so a guest upgrading mid-session doesn't land back on a stale form. When a guest plants their **first tree**, the dashboard swaps the "new tree" snackbar for a **one-time** account-upgrade bottom sheet (`AuthService.shouldOfferAccountUpgrade` / `markAccountUpgradeOffered`, key `guest_account_prompt_shown_v1`) — after that, the launch screen's Register button is the only nudge. Sign-up is just email+password, but it is **email-verified**: when Supabase "Confirm email" is on, `signUp` creates no session, so `LoginScreen` pushes [VerifyEmailScreen](lib/screens/auth/verify_email_screen.dart) where the user enters the 6-digit code emailed to them (`AuthService.verifyEmailOtp` → `verifyOTP(OtpType.signup)`, with `resendSignupOtp`); verifying creates the session and the gate advances (a sign-in attempt that throws `email_not_confirmed` is routed there too). **Requires dashboard config**: enable Confirm email and put `{{ .Token }}` in the "Confirm signup" email template so a code (not just a link) is sent. After verification **every account must claim a username**, so the gate sends any signed-in user without a profile through the forced [OnboardingScreen](lib/screens/onboarding_screen.dart) (username + optional display name) before the app opens — where **Acorn** (the `AcornMascot`) greets them in a speech bubble whose line reacts to the form state (welcome / busy / error). It's offline-first: once a user onboards, `ProfileService.markOnboardedLocally()` records their id locally (`onboarded_user_id_v1`) so later launches skip the network profile lookup; a profile-fetch failure shows a retry rather than locking the user out.

**Persistence — offline-first cache synced to Supabase.** Source of truth is **Supabase** (Postgres + email/password auth); `shared_preferences` is a local **write-through cache** so reads stay instant. The seam is [SyncedStore<T>](lib/services/synced_store.dart): reads return cache immediately then refresh in the background; writes hit cache first, then upsert/delete to Supabase (queued in a per-collection pending list when offline). There is also a `loadCached()` (mirrored as `BudgetRepository.loadCached` / `GoalRepository.loadCached`) that reads the cache with **no** background refresh, for callers that write based on what they read and must not race their own writes against a pull that overwrites the cache wholesale — the pay-cycle sweep uses it. The four stores keep their original static API (`loadAll`/`saveNew`/`update`/`delete`) and local cache keys, each delegating to a `SyncedStore`:
- [BudgetRepository](lib/services/budget_repository.dart) — cache `budget_tree_v1`, table `budgets`
- [GoalRepository](lib/services/goal_repository.dart) — cache `goals_v1`, table `goals`
- [CategoryRepository](lib/services/category_repository.dart) — cache `tree_categories_v1`, table `categories`
- [AchievementService](lib/services/achievement_service.dart) — cache `ach_unlocks_v1`, table `achievements`
- [CheckInRepository](lib/services/check_in_repository.dart) — cache `check_ins_v1`, table `check_ins` (migration `20260808120000_check_ins.sql`)

Each Supabase table is keyed `(user_id, id)` with the whole model in a `data jsonb` column under per-user RLS, so **the toJson/fromJson rule still governs: when you add a model field, update both and keep the fallback** — it maps straight into `data`, no schema change needed. [test/model_roundtrip_test.dart](test/model_roundtrip_test.dart) enforces this: it sets every field of `BudgetModel`, `Goal`, `TreeCategory` and the achievement entry to a non-default value and asserts the round trip preserves it, so a new field wired into only one half fails there instead of silently vanishing on the next pull. Add your field to that test too. [AuthService](lib/services/auth_service.dart) (`AuthService.instance`, mirrors AppSettings) wraps Supabase auth; [SyncEngine](lib/services/sync_engine.dart) handles first-login migration (push local rows up, then pull), flush-on-resume/reconnect, and clear-caches-on-signout. No dart-defines → everything degrades to local-only mode. Schema lives in [supabase/migrations/](supabase/migrations/). **`citext` lives in the `extensions` schema, not `public`** (moved by `20260802221910` to clear a security advisor finding), so a migration referring to the type unqualified needs `extensions` on its search path; `profiles.username` is unaffected because the column references the type by OID, and PostgREST resolves the `=` / `ILIKE` operators through its own `public, extensions` path.

**Social layer — profiles, friends & shared goals (online-only).** Distinct from the four offline-first stores: the social services talk to Supabase **directly** and no-op when unconfigured/signed-out (they gate on `SupabaseConfig.isConfigured && AuthService.instance.isSignedIn`, surfacing an "online required" UI). While loading, both screens show layout-shaped skeleton placeholders ([lib/widgets/skeleton.dart](lib/widgets/skeleton.dart): `SkeletonPulse`/`SkeletonBox` + `FriendsSkeleton`/`ProfileSkeleton`, pulse gated on reduced motion) instead of bare spinners. Two extra tables (real columns, *not* the `data jsonb` pattern): `profiles` (**not bulk-readable**: SELECT is your own row plus anyone you share a `friendships` row with in *either* direction and at *any* status — pending is deliberately included, since a request has to render the requester's name before you can accept it. Finding a stranger goes through the SECURITY DEFINER `search_profiles(q)` / `username_available(candidate)` functions instead, which re-derive the caller from `auth.uid()`, cap the result set, require 2+ characters and return only the columns a search row renders, never `bio` or the status fields. Migration `20260803180819_restrict_profile_reads.sql`. The advisor will list these two as "signed-in users can execute a SECURITY DEFINER function" — that is intentional and is the documented escape hatch for this pattern. Their `search_path` must keep `extensions` on it, since `username` is citext.) One row per user — unique `username`, optional `display_name`, free-text `bio`, plus `status_mode`/`status_goal_id` controlling how the user's status emoji is derived, and `last_seen_at` for presence) and `friendships` (`(requester, addressee, status)`; **`status` is the authorization key for the whole social layer** — the goals share policy, the messages INSERT policy and the goal_likes INSERT policy all reduce to "is there an accepted row joining these two users", so it is constrained to `pending|accepted` by a CHECK, INSERT is forced to `pending`, and accepting is addressee-only `pending -> accepted`. `requester`/`addressee` are frozen by **column privilege** (`revoke update ... ; grant update (status)`) rather than by policy, because a WITH CHECK only ever sees the new row and so cannot pin a column against its old value. Migration `20260803175958_fix_friendship_consent_bypass.sql`; don't loosen any of it). Privacy is **per-goal**: `Goal.sharedWithFriends` (default false, the single privacy toggle on [GoalDetailScreen](lib/screens/goal_detail_screen.dart)) gates an *additive* `"friends read shared goals"` SELECT policy on the `goals` table — an accepted friend can read only goals the owner marked shared. **Budgets are never shared.** A **profile** is just `username` + `bio` + the goals the user shared, drawn as saplings in a grid (the [GoalSaplingCard](lib/widgets/goal_sapling_card.dart), which renders each sapling in its goal's saved tree colour via `Goal.leafColorValue` and a `FittedBox` so the tree always fits the cell; completed goals read golden). The user sees their own via the dashboard's top-right profile button ([ProfileScreen](lib/screens/profile_screen.dart), bio editable there); a friend sees the same view via [FriendGardenScreen](lib/screens/friend_garden_screen.dart) (name + bio header + shared-goal grid). Tapping a sapling opens the goal: on your own profile that's the editable [GoalDetailScreen](lib/screens/goal_detail_screen.dart); on a friend's it's the **read-only** [FriendGoalScreen](lib/screens/friend_goal_screen.dart) (sapling in the owner's colour + progress, no deposit/edit/delete/share controls — friends can never alter your goals, which RLS also enforces; laid out as a Column mirroring GoalDetailScreen so the whole tree is always visible, guarded by [test/friend_goal_layout_test.dart](test/friend_goal_layout_test.dart)). Because categories are **never** synced between users, a goal carries a denormalised `leafColorValue` (its category's `colorValue`) in its `data` jsonb so a friend renders the same colour the owner saved; it's set when a goal is created/edited and backfilled-then-persisted when the owner opens their own ProfileScreen. (There is **no "featured goal"** mechanic — it was removed; the only goal-sharing control is the per-goal privacy toggle.) Profiles also carry an optional **profile picture** picked from the device gallery (`image_picker`, resized to ~256px JPEG on device and stored inline as base64 in `profiles.avatar_b64`, migration `20260706120000_profile_avatar.sql`; rendered by [ProfileAvatar](lib/widgets/profile_avatar.dart) on the own-profile header, friend tiles, and the friend garden app bar; iOS photo permission is declared in Info.plist). Services: [ProfileService](lib/services/profile_service.dart) (claim username, search, set status mode, set bio, set avatar, `touchPresence`), [FriendsService](lib/services/friends_service.dart) (requests, accept/remove, a friend's shared goals + assembled `FriendSummary`), and the pure [FriendStatus](lib/services/friend_status.dart) util (goals → one status emoji via the friend's `FriendStatusMode`). **Likes & messages** (migration `20260718021503_likes_and_messages.sql`): `goal_likes` (`(goal_owner, goal_id, liker)` PK; RLS reuses the goals table's own policies via `exists (select from goals)` so "can like/see likes" = "can read the goal" — insert additionally requires shared + not your own goal) drives the heart pill on [FriendGoalScreen](lib/screens/friend_goal_screen.dart) (`_LikePill`: optimistic toggle + tally + elastic pop, needs the `ownerId` param) and a passive tally chip on the owner's GoalDetailScreen (`_loadLikes`, shown only when shared and count > 0), via [GoalLikesService](lib/services/goal_likes_service.dart) (`summary`/`like`/`unlike`). `messages` (immutable 1:1 rows, body capped 1..500 by a DB check constraint mirrored in `MessagesService.maxLength`; RLS: participants read, sender must be an accepted friend) powers [FriendChatScreen](lib/screens/friend_chat_screen.dart) (bubbles + composer, polls every 4s while open, no realtime socket) via [MessagesService](lib/services/messages_service.dart) (`thread`/`send`); the chat opens from the chat icon in the FriendGardenScreen app bar. Username is claimed during onboarding (the forced [OnboardingScreen](lib/screens/onboarding_screen.dart) behind `OnboardingGate`) — required for **every** account, not just those who want friends. `ProfileService.claimUsername` accepts an optional `displayName` and marks the user onboarded locally on success; `FriendsScreen` still carries a `_ClaimUsername` fallback for the unconfigured-then-configured edge.

**App-wide settings.** [AppSettings](lib/services/app_settings.dart) is a `ChangeNotifier` singleton (`AppSettings.instance`) persisting palette, text scale, reduced-motion, the tutorial-seen flag, a `soundEnabled` toggle, an `aiCoachEnabled` toggle (master switch for the AI coach), and notification preferences (per-type toggles for budget warnings / streak reminders / weekly summary / goal watering reminders, plus the scheduled hour/minute/weekday for each, including `notifGoalWatering` + `waterHour`). Each setting has its own `settings_*_v1` key. UI reads `palette`/`textScaleFactor`/`motionMultiplier` from it; the whole app is theme-reactive through the listener in `main.dart`. Changing a notification setting should re-run `NotificationScheduler.rescheduleAll()`. It also holds the app `locale` (`settings_locale_v1`, null = follow device) used by a Language picker in Settings — see Localization below.

**Localization (i18n).** Flutter `gen-l10n`: strings live in ARB files under [lib/l10n/](lib/l10n/) (`app_en.arb` is the template, plus `app_fr.arb`, `app_es.arb`); `flutter gen-l10n` (or any build) regenerates `AppLocalizations` (also in `lib/l10n/`, committed). `main.dart` wires `localizationsDelegates`/`supportedLocales` and `locale: AppSettings.instance.locale`, so the Settings language picker (English / Français / Español / System) flips the whole app live. In widgets read strings via `AppLocalizations.of(context).<key>` (non-null getter). **To add a string: add the key to all three ARB files, run `flutter gen-l10n`, then reference it.** The **whole app is localized** — every screen, dialog, the Acorn tutorial dialogue, achievements, allocation suggestions, and notifications, down to the Android **notification channel** names/descriptions shown in OS settings (`notifChannel*` keys, resolved by `NotificationService._channelCopy(channelId)`, which is why `_details` takes only a channel id) and the default budget name (`defaultBudgetName`, seeded into the wizard's name field in `didChangeDependencies` since a field initialiser has no context). The only deliberately untranslated string is the brand name "Budget Tree". Patterns to reuse: data/model labels live in `lib/l10n/` extension helpers (`goal_labels.dart`, `achievement_labels.dart`, `preset_labels.dart`); background code with no `BuildContext` (notifications) resolves strings via `appLocalizations()` in `app_localizations_resolver.dart`; pure services/data functions that produce copy take an `AppLocalizations` param (e.g. `SuggestionService.forBudget`, the `tutorial_content.dart` functions). **Never hardcode user-facing copy, and never use dashes in it** (em-dashes/hyphens read as AI — reword; ranges become "3 to 20", clauses become separate sentences). Mandatory French grammar hyphens (e.g. `Connectez-vous`) are the only exception.

**Theming is token-driven.** The app has the modern minimal look: warm beige canvas (`#F1EBDE`), soft cream cards with gentle shadows, color delivered through flat illustrations and a fresh green accent. ### Domain model

- **Budget** ([budget_model.dart](lib/models/budget_model.dart)): `BudgetModel` (tree) → `IncomeSource`s + `ExpenseCategory`s (branches). An `IncomeSource` carries its own arrival rhythm (`frequency`, a nullable **[Rhythm](lib/data/rhythm.dart)**; null = legacy "once per cycle") and `amountPerCycle(cycle)` converts it into the budget's cycle via `periodsPerMonth` ratios — so a $2000 bi-weekly salary counts as ~$4333 in a monthly budget. An `ExpenseCategory` carries the **same rhythm mechanic for bills**: `frequency` (nullable, null = once per cycle) with `allocatedPerCycle(cycle)` / `setAllocatedPerCycle(perCycle, cycle)`, so $1200 monthly rent in a weekly budget reads as a ~$277 per-cycle **set-aside** (surfaced as advice in the wizard's branch list, the branch detail sheet's `setAsideEachCycle` line, and the forest edit sheet, which also lets each branch's rhythm be edited). `BudgetModel.payFrequency` doubles as **the budget's cycle**: `totalIncome` sums `amountPerCycle(payFrequency)` and `totalAllocated`/`percentageFor`/`remaining` sum `allocatedPerCycle(payFrequency)`, keeping both sides like-for-like (tested in [test/income_cycle_test.dart](test/income_cycle_test.dart)). `PayScheduler` credits linked goals with the branch's **per-cycle** allocation for each elapsed period; AI `budget_plans` payloads convert expense amounts to per-cycle before sending, and applied plan amounts convert back into the bill's own rhythm. An `ExpenseCategory` holds `linkedGoalIds` connecting a branch to goals. Derived getters: `totalIncome`, `totalAllocated`, `remaining`, `percentageFor`. **[Rhythm](lib/data/rhythm.dart) is the type all three carriers use** (`IncomeSource.frequency`, `ExpenseCategory.frequency`, `BudgetModel.payFrequency`): it wraps either one of the four `PayFrequency` presets or a user-typed **custom interval** (`Rhythm.every(3, CadenceUnit.weeks)`). Everything downstream reads `periodsPerMonth` / `periodLength` / `wire` off it, so a custom interval converts, schedules and auto-funds exactly like a preset. **Persistence is backwards compatible**: a preset encodes to the bare `PayFrequency` index it always used, so pre-existing rows decode unchanged; only custom rhythms write `{count, unit}`. `rhythmFromJson` accepts both plus null. Display names are localized via [lib/l10n/rhythm_labels.dart](lib/l10n/rhythm_labels.dart) (presets defer to `pay_frequency_labels.dart`; custom reads "Every 3 weeks" through an ICU plural). The shared [RhythmPicker](lib/widgets/rhythm_picker.dart) renders the four preset chips plus **Custom**, which reveals a count field and a days/weeks/months dropdown; `showRhythmDialog` is the compact variant for the forest edit sheet. The edge function parses the `every:N:unit` cycle token into words. Covered by [test/rhythm_test.dart](test/rhythm_test.dart).
- **Goal** ([goal_model.dart](lib/models/goal_model.dart)): a sapling. `targetAmount <= 0` means **uncapped** (`isUncapped`) — it grows forever through size `tier`s (1–6) on a log curve; capped goals use linear `progress` 0..1 and a `stage` 0–5. Visual growth/scale (`progress`, `stage`, `tier`, `tierScale`, `stageName`) all derive from these — don't store visual state. Every deposit/withdrawal is recorded in `contributions` (`List<Contribution>`, each dated and sourced: manual / auto / adjustment) — this ledger is the source of truth for streaks, comparisons, and achievements. The legacy `currentAmount` field still persists for back-compat; keep both in sync. **Completion is a durable trophy**: `isComplete` is the live "at/over target" check, but `completedAt` is stamped once (via `stampCompletionIfReached()`) and **never cleared** — `isCompleted` (`completedAt != null`) stays true even after a withdrawal and drives the golden card border + "Completed" filter on GoalsScreen and profile featuring. `sharedWithFriends` (default false) opts the goal into the social read policy (see the Social layer above). `leafColorValue` (nullable int) is a denormalised copy of the goal's category colour so a shared goal carries its tree tint to friends who can't see the owner's categories (null falls back to forest green). A goal can also carry a **watering schedule** (`waterAmount`, `waterCadenceIndex` → a [WaterCadence](lib/data/water_cadence.dart) weekly/biweekly/monthly, `nextWaterDate`, `waterRemindersEnabled`) set in the goal wizard; it drives reminder notifications only (the user still deposits manually). `advanceWatering()` rolls `nextWaterDate` forward past missed slots; a manual deposit on [GoalDetailScreen](lib/screens/goal_detail_screen.dart) pushes it one cadence out and reschedules. **`waterAnchorDate` is the immutable start of the watering series and is not the same thing as `nextWaterDate`**, which is a *cursor* (reset to `now + cadence` on every manual deposit, and rolled forward in memory by `NotificationScheduler`). Check-ins enumerate watering slots as `anchor + cadence * n`, which only reproduces run to run because the anchor never moves. Set once at creation; legacy rows fall back to `nextWaterDate` in `fromJson`.
- **CheckIn** ([check_in.dart](lib/models/check_in.dart)): one pay day or watering, and how it went. `kind` (payday/watering), `subjectId` (budget or goal id), `dueAt`, `verdict` (`onTrack`/`slipped`/`offPlan`), an optional `List<BranchActual>` (`name`/`planned`/`actual`), and `missed`. See the check-ins section below.
- **TreeCategory** ([category_model.dart](lib/models/category_model.dart)): user tag shared by budgets and goals; its `colorValue` drives leaf color. Created **and deleted** via [CategoryPicker](lib/widgets/category_picker.dart) (tap "New" to add; long-press a category chip to delete — budgets/goals that referenced it just lose their tint, no cascade). `CategoryRepository.delete(id)` removes it.
- **Achievement** ([achievement.dart](lib/models/achievement.dart)): badge definition + `AchievementStats` (aggregate facts unlock tests read) + `AchievementCatalog` (predefined badges the service evaluates).

**Editing a saved tree & leftover money.** The forest grid card's edit sheet edits the tree name, category, branch amounts + charge rhythms, AND the roots (income sources: name, amount, arrival rhythm, add/remove) — and preserves `payFrequency`/`firstPayDate`/`lastProcessedAt` so an edit never resets the pay engine. When a budget has leftover (`remaining > 0`), the expanded forest card offers "Grow a goal with it": [routeLeftoverToGoal](lib/services/leftover_to_goal.dart) lets the user pick or quick-create a goal and appends a linked funding branch (same mechanic as the wizard's leftover step). The Gardener's Tips sheet on the budget tree ([SuggestionService](lib/services/suggestion_service.dart)) is goal-aware: pass `goals:` and it suggests a watering branch for every active goal the budget doesn't feed, plus a savings branch when leftover is large (>25% of income or >$200).

### Pay-cycle engine

[PayScheduler](lib/services/pay_scheduler.dart) is the core financial logic. `runUpdate(budget)` figures out how many whole pay periods elapsed since `budget.lastProcessedAt` (using `payFrequency` from [pay_frequency.dart](lib/data/pay_frequency.dart)) and credits each branch's allocation share to its linked goals, respecting target caps, then advances `lastProcessedAt` by exactly the processed periods (not to "now") and persists touched goals/budget. Completion is stamped through `Goal.stampCompletionIfReached()` so the rule lives in one place. It's a pure-ish static utility — keep new financial math here, not in widgets.

**`runAllDue()` is the sweep that actually drives it.** `runUpdate` alone only fires when the user opens a tree, so budgets they never visit would never fund their linked goals (and the streaks / comparisons / achievements that read the ledger would all understate). `runAllDue()` runs `runUpdate(budget, fromCache: true)` for **every** budget with `savedAt`, `payFrequency` and `firstPayDate` set, skipping drafts, swallowing per-budget failures, and returning how many budgets actually moved money. It is idempotent (a second sweep in the same period finds nothing) and guarded by a `_sweeping` flag against overlap. **Ordering matters**: for a signed-in user the sweep runs at the end of `SyncEngine.onSignedIn()` and `SyncEngine.flushAndPull()`, i.e. *after* the pull has landed, so it never writes against a cache that is about to be replaced; `main.dart`'s `_sweepPayCyclesIfLocalOnly()` covers the cases the sync engine never touches (guest mode, no dart-defines) on boot and on resume. Covered by [test/pay_scheduler_test.dart](test/pay_scheduler_test.dart) (multi-period catch-up, the `lastProcessedAt` advance, caps, idempotency). (There is **no tax feature** — tax estimation was removed; `BudgetModel.age`/`location` linger only for back-compat and are no longer collected.)

### Check-ins & tree health

**Check-ins are the app's only record of what the user actually *did*.** Everything else describes a plan. There is still no per-category spend log, so the optional per-branch `actual` amounts on a check-in are the **only** plan-versus-actual data anywhere in the system — anything that wants to talk about overspending must come from there and must have a real empty state, because a user who never fills them in has none.

[CheckInService](lib/services/check_in_service.dart) derives, resolves and reads them back. Three rules that are load-bearing:

1. **Only *resolved* check-ins are persisted; pending ones are derived in memory on every read.** `SyncedStore.update` replaces a row wholesale and `pull()` overwrites the cache after flushing the offline queue, so a re-derived pending row would erase another device's confirmation. Storing only resolved rows makes every write monotonic (pending becomes confirmed or missed, never the reverse), so replays are idempotent and there is nothing to merge. It also means editing a budget's pay schedule re-derives the pending set while leaving the answered history alone. **Don't start persisting pending rows.**
2. **A per-install epoch** (`check_ins_epoch_v1`, stamped on first `sync()`) floors all generation. The create wizard's date picker allows a first pay date two years back, so without it an existing user's first launch backfills a pile of already-lapsed check-ins and the feature debuts with a dead tree.
3. **Dates that reach the user come from `PayScheduler.payDateAt`/`elapsedPayDates`, not `nextPayDate`/`periodsBetween`.** The engine's epoch-millisecond math over `Rhythm.periodLength` calls a month 30 days, which is fine for *counting* periods (and is pinned by `test/pay_scheduler_test.dart`) but drifts a monthly budget anchored 31 January to "27 December" by its twelfth pay date. The new helpers walk the calendar via `addDays`/month arithmetic with last-day clamping. **The engine counts periods; the check-in names dates.** Keep both.

`sync()` runs strictly *after* `PayScheduler.runAllDue()` everywhere (chained in `main.dart`'s local-only path, awaited in `SyncEngine.onSignedIn`/`flushAndPull`), has its own `_syncing` re-entrancy flag, and its only unprompted write is pending → missed once the grace window (half a period, clamped 2 to 7 days) lapses. Covered by [test/check_in_service_test.dart](test/check_in_service_test.dart).

**[TreeHealthService](lib/services/tree_health_service.dart)** turns that ledger into one 0-to-100 consistency signal, in the spirit of Opal's gem: consistency grows it, lapsing walks it backwards. Replays the last `historyWindow` (60) resolved check-ins from a baseline of 50 — `onTrack +8`, `slipped +3`, `offPlan -2`, `missed -10`, clamped 0..100 — into five `TreeHealthTier`s (barren/wilting/steady/flourishing/radiant at 0-19/20-39/40-59/60-84/85-100). The asymmetry is deliberate: a miss must cost more than an answer earns or a healthy tree never visibly reacts, but roughly four good check-ins undo three misses so recovery is always in reach. **The score is derived, never stored**, so two devices always agree and it can't drift from the history behind it.

[HealthTreeView](lib/widgets/health_tree_view.dart) draws it from the shared `TreeDrawing` primitives, with health driving three cues at once (canopy clusters drop away, `LeafPalette.withHealth` drains the four stops toward dry amber, fallen leaves appear below half health, and a breathing halo at radiant). It is **its own widget, not a flag on `StaticBudgetTreeView`** — a budget tree means "your allocation" and must never be recoloured by behaviour. Covered by [test/tree_health_test.dart](test/tree_health_test.dart).

### Retention & engagement

A cluster of static-utility services drives streaks, badges, and reminders off the goal contribution ledger — keep this logic here, not in widgets:
- **StreakService** — weekly contribution streaks from the ledger.
- **PulseService** — pure picker for the dashboard's [PulseStrip](lib/widgets/pulse_strip.dart) (rendered above the ReflectionBanner): returns the single most useful nudge in priority order — watering due/overdue (earliest `nextWaterDate`, deep-links to GoalDetailScreen) → streak at risk → quiet streak badge (both open GoalsScreen) → "plant your first tree" for empty accounts → hidden. The strip is the in-app face of the watering/streak habit (notifications are the out-of-app one); the dashboard refreshes it via a `GlobalKey<PulseStripState>` after every navigation. Unit-tested in [test/pulse_service_test.dart](test/pulse_service_test.dart).
- **ComparisonService** — week-over-week / month-over-month savings & allocation deltas.
- **SuggestionService** — allocation suggestions surfaced to the user.
- **AchievementService** — evaluates `AchievementCatalog` against `AchievementStats` and persists unlocks.
- **NotificationContent** — pure copy + severity logic. Note: a "budget warning" measures allocation-vs-income (there is no per-category spend log).
- **Calendar accuracy.** Day arithmetic goes through [lib/data/calendar.dart](lib/data/calendar.dart) (`dateOnly` / `addDays` / `daysBetween` / `weekIndexOf` / `startOfWeek`), **never `Duration(days: n)` or `difference(...).inDays`**. Those add 168 hours rather than a week and truncate rather than round, so across a daylight-saving transition they slip an hour and then a whole day: the old `StreakService.weekIndex` disagreed with the correct value on **every Monday during DST** (68 days out of two years in a US zone), silently filing a deposit into the previous week. Day counts go through UTC (no transitions, so exact) and day stepping through the `DateTime` constructor (normalises overflow, re-resolves the wall clock). Covered by [test/calendar_test.dart](test/calendar_test.dart).

**Time zone.** Reminders are wall-clock times, so the zone decides when they actually fire. `AppSettings.timeZone` (`settings_timezone_v1`, null = follow the device) is applied by `NotificationService.applyTimeZone()`, which prefers the user's override, falls back to the device, and only then to UTC. Settings → Language & region offers a searchable list of every IANA zone (`NotificationService.availableTimeZones()`); changing it re-applies the zone **and** re-runs `rescheduleAll()`, since reminders already handed to the OS keep their old absolute firing times.

- **NotificationScheduler** — decides *what* to schedule (budget warnings, daily streak reminder, weekly summary, and **per-goal watering reminders**); **NotificationService** is the thin OS wrapper over `flutter_local_notifications` (channels: budget_warnings, streak_reminders, weekly_summary, goal_watering) that degrades failures to no-ops. Watering reminders are one-shot `zonedSchedule` notifications: for each goal with a schedule, `rescheduleAll()` seeds a "due in 2 days" heads-up and a "due today" nudge (at `AppSettings.waterHour`) and re-seeds the next occurrence on every boot/resume/deposit. **OS permission is requested on opt-in, not at boot**: `rescheduleAll()` only calls `NotificationService.requestPermissions()` once `AppSettings.notifPermissionAsked` is set, which happens when the user touches the Settings notifications card or saves a goal with "Remind me to water" on — a fresh install never opens with a permission dialog.
- **SoundService** — tactile/audible feedback, gated on `AppSettings.soundEnabled`.

### AI coaching (smart plans + reflections)

Claude (Sonnet) is woven into the core flows through a Supabase **edge function** ([supabase/functions/ai-coach/index.ts](supabase/functions/ai-coach/index.ts)) — the architecture is App → Edge Function → Anthropic API, so the `ANTHROPIC_API_KEY` stays server-side (set as a Supabase secret, never in the app). The function is one router switched on an `action` field with three actions, each returning strict JSON the app parses defensively: `budget_plans` (income + expenses each with an optional fixed amount + a **lifestyle questionnaire** (`survey`, question→answer) + an optional free-text note + the budget's `cycle` (`PayFrequency.wire`) so the coach scales estimates to the period, since amounts are per cycle rather than always monthly → 2-3 allocation plans that keep any fixed amounts and estimate the blanks from the survey), `goal_plans` (switched on `mode`: **`byDate`** when the user named a deadline, **`byAmount`** when they didn't) — **the app computes every amount and date itself with [GoalPlanMath](lib/services/goal_plan_math.dart) and sends them in; the model only writes the rationale for each**, and any number it returns is ignored by the client. That split is the fix for a chosen date not being honoured: the model's arithmetic drifted, and `reflection` (a compact period summary → 2-4 sentences of prose). The app sends **already-computed summaries**, never raw rows, so the function is stateless and cheap. The AI writes its prose in the app's active locale (passed as `locale`). Model is pinned to `claude-sonnet-4-6`.

Client side, everything is **online-only and degrades gracefully** (same gating as the social layer):
- [AiCoachService](lib/services/ai_coach_service.dart) (`AiCoachService.instance`) wraps `functions.invoke('ai-coach', ...)`, gated on `SupabaseConfig.isConfigured && AuthService.instance.isSignedIn && AppSettings.aiCoachEnabled`; it throws a typed `AiUnavailable` on any failure so callers fall back. DTOs in [lib/models/ai_plan.dart](lib/models/ai_plan.dart) (`AllocationPlan`; `GoalPlanOption` carries a `WaterCadence` + `perWatering` with a derived `monthly`; `GoalPlanResult`).
- **Budget creation** ([createbudget_screen.dart](lib/screens/createbudget_screen.dart)) is a **5-step wizard**: Income → Expenses → **Survey** → **Plan** → **Finish**. Settling the plan advances to a dedicated `_FinishStep` (tree name, pay schedule, first pay date, and the "grow a goal with your leftover" card) where the bottom bar becomes "Plant My Budget Tree"; these used to be revealed below a settled plan, where the user had to scroll to find them. Each income gets its own arrival-rhythm chips ("How often does it arrive?") and the running list shows the per-cycle conversion (`approxEachCycle`) when the rhythms differ. The Plan step's pay card repeats the same cycle chips (still adjustable) plus the first-pay-date picker. Changing cycle/income resets `_planSettled`. **Every phase uses progressive disclosure** (the survey's one-at-a-time feel, generalised): a step opens with just its first box and reveals the next only after the user confirms the current one, via the shared `_Reveal` (fade + slide-in on first build) and `_ContinueButton` widgets. **The add boxes themselves are staged**: each opens with just the name + amount row and reveals the next question only once that's filled in, ending in a full-width labelled button (`addThisSource` / `addThisExpense`) rather than a round add icon. Income asks name+amount → **how often does it arrive** → Add. Expenses asks name+amount → **how often is it charged** → **which branch does it belong to** → Add, where the branch chips are a real category picker that only fills a blank name (so picking "Subscriptions" never overwrites "Netflix"). Both steps also show a **saved entries card** ([SavedEntries](lib/services/saved_entries.dart)) offering one-tap reuse of roots and branches from the user's earlier trees, derived from the saved budgets rather than stored separately (no new table, de-duplicated by name, newest first, hidden for a first-time user). Adding sources reveals the list, then a "That's all my income" button reveals the **budget cycle** card (`_payFrequency`, default monthly, so every later amount reads "per cycle"). Expenses has a matching "That's all my expenses" confirm button unlocking Next. **Tests that type into an add box must settle before reaching for its button** — `enterText` doesn't pump a frame, so the revealed button isn't in the tree yet. The **"where you stand" meter is pinned** above the scrolling content of both the Expenses and Plan steps (`_AllocationStrip`: allocation bar + allocated/remaining, amounts in `FittedBox`es so the full number always shows, red border when over) so what's left to allocate is never out of sight. Each expense also gets **charge-rhythm chips** ("How often is it charged?", `expenseCharged`) mirroring income's arrival chips, and the branch list shows the bill's rhythm plus its `approxEachCycle` set-aside when the rhythms differ. Reveal state lives in the parent (`_incomeConfirmed` / `_expensesConfirmed`, reset if the list is emptied) and **gates the bottom bar's Next**, so the disabled Next signals "finish this box". Next is additionally gated by a **scroll-through gate** (`_seenEnd`/`_noteScrollMetrics`, fed by `ScrollNotification` + `ScrollMetricsNotification` listeners around the step switcher): the user must have scrolled to the end of the current step before advancing, steps whose content fits pass automatically, and revealed content that grows past the fold re-arms the gate; when the gate is the only blocker the bottom bar shows a localized "scroll to the end" hint (`scrollToContinue`). Tests that drive the wizard must scroll to the end of a step before tapping Next (see the `scrollToEnd` helper in [test/create_budget_over_budget_test.dart](test/create_budget_over_budget_test.dart)). **Over-budget is a hard stop**: tapping Next on the Expenses, Plan or Finish step while `_totalAllocated > _totalIncome` doesn't advance — Acorn pops up (`showTutorialDialog`, `tutOverBudget1/2`) telling the user how far over they are and to trim before continuing (tested in [test/create_budget_over_budget_test.dart](test/create_budget_over_budget_test.dart)). The Plan step's finishing-touch cards are wrapped in `_Reveal` too. Income/Expense steps are intentionally decluttered (one hero input + a running list). The income step's eleven example source names are folded behind a quiet **"View suggestions"** toggle (`_SuggestionToggle`) rather than filling the card before the user has typed anything. Expense amounts stay **optional**. The **Survey** step (`_SurveyStep`, questions defined in [lib/l10n/survey_labels.dart](lib/l10n/survey_labels.dart)) holds a bank of **~20 budgeting questions** but only asks the ones that apply: each `SurveyQuestion` can carry a `visibleIf(answers)` predicate, and `visibleSurveyQuestions(answers)` is what the step walks and what `_surveyForAi` sends, so someone with no children is never asked about childcare and a renter is never asked about property upkeep (a typical run is 12 to 15 questions; branching is pinned by [test/survey_branching_test.dart](test/survey_branching_test.dart)). Changing a trigger answer retires its follow-up from both the walkthrough and the prompt. It shows them **one question at a time**: tapping an answer auto-advances (short delay so the selection lands visually), each question has a Skip, a thin progress bar tracks position, and previously settled questions render as compact tappable recap rows so any earlier answer can be edited; once every question is answered/skipped it settles on a summary view with the optional free-text note. Answered/skipped state lives in the parent (`_surveyAnswers` / `_surveySkipped`) so leaving and re-entering the step resumes at the summary. Answers are sent to `budget_plans` as `survey` so the coach can estimate the blank expenses. The **Plan** step renders the coach's [AllocationPlanCard](lib/widgets/allocation_plan_card.dart)s (pick one or set amounts manually), and once settled offers **"Grow a goal with your leftover"**: route the remaining money to a new or existing goal, which appends an `ExpenseCategory` branch linked to that goal (`linkedGoalIds`) so `PayScheduler` auto-funds it.
- **Goal creation** ([create_goal_screen.dart](lib/screens/create_goal_screen.dart)) is a **3-step wizard** (Goal + amount → Timeframe → Watering plan). The Timeframe step asks **"do you have a date in mind?"**, and that answer picks which way the plan is solved: **with a date** we compute the exact per-watering amount that lands on it (`GoalPlanMath.perWateringForDate`, day-accurate rather than calendar-month approximate, so the date is met precisely); **without one** the plans are three deliberate **progressions**, gentlest first, built from the least and the most the user says they'd part with each timeframe (`_WillingRangeCard`, asked before anything is generated): their floor (`GoalPace.easy`, latest finish), the midpoint (`steady`), and their ceiling (`fast`, soonest finish). Each carries the date it lands on via `dateForPerWatering`, and the card names the pace since that's what distinguishes them. With no range given it falls back to a spread anchored on spare income (`suggestedPerWatering`). The custom card also shows "reaches it by …" live as the user types. Either way the maths is local and exact, and an AI failure leaves the plans unexplained rather than unusable. Covered by [test/goal_plan_math_test.dart](test/goal_plan_math_test.dart); both wizards use the shared [StepProgress](lib/widgets/ui/step_progress.dart) segmented bar (the old vine indicator is deleted). The Watering step **asks whether to use the coach** (`_AiPrompt`); AI plans come back as selectable **watering** cards ("$X every 2 weeks", `_WaterPlanCard`), there is always a **Custom** card (cadence chips + per-watering amount), tappable alternative dates, and a **"Remind me to water"** toggle. **Leaving the custom amount blank means "you pick it"**: `_suggestedPerWatering(cadence)` fills it with the exact figure for the chosen date, shown live as the field's hint and helper text. Note the plans **all imply the same monthly total by design** — with the target date fixed, $34 weekly and $68 biweekly are the same money — so each card prints the shared monthly equivalent and the prompt forbids justifying a plan as cheaper or faster, requiring instead that each rationale says who that *rhythm* suits. Genuinely different commitments come from the alternative completion dates. Manual/offline uses [GoalPlanMath](lib/services/goal_plan_math.dart) (`monthlyToReach`/`perWateringToReach`/`monthsForPerWatering`). After saving it still offers to **link a budget branch** for auto-funding. `freeMonthlyIncome` (sum of budgets' remaining) is fed into the AI call.
- **Reflections** ([ReflectionService](lib/services/reflection_service.dart)): on boot/resume, `maybeGenerate()` checks whether a new weekly/monthly reflection is due (prefs-based dedupe), builds the summary from `ComparisonService`/`StreakService`/budgets/linked goals, calls the `reflection` action, caches the latest in `SharedPreferences` (so it shows offline) AND upserts to the `ai_reflections` table (per-user RLS, [migration](supabase/migrations/20260628140000_ai_reflections.sql)), then fires a local notification. The dashboard shows the latest via [ReflectionBanner](lib/widgets/reflection_card.dart); `NotificationScheduler` uses the cached reflection text as the scheduled weekly-summary body when present. Toggle: `AppSettings.aiCoachEnabled` (Settings → AI Coach).
